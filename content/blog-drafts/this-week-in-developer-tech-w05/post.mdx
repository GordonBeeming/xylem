A DevOps laptop that can submit withdrawals is enough to move funds when the signing service signs what that laptop asks for. Text hidden in a GitHub issue becomes a shell command when a workflow interpolates that text into a `run` step.

This edition draws on the 30 October to 5 November 2026 briefings, with five selected stories on wallet signing, Claude plan limits, GitHub Actions, the Brotli decoder and Git at agent scale. Earlier incident dates are kept with the relevant stories.

## 1. A Binance theft ran from a DevOps laptop into the signing system

TRM Labs' analysis and the SOCtember breakdown describe an attacker draining about US\$6.36 billion (roughly A\$9 billion, an estimate) from Binance wallets on 10 blockchains. The drain happened on Thursday evening UTC, early Friday 30 October Brisbane time, and most of the funds moved in about 20 minutes. TRM attributes the theft with high confidence to North Korea's TraderTraitor unit. Binance says its first look points to a compromised DevOps engineer's laptop that gave the attacker a service container able to submit withdrawals, and that it has found no sign of a private key leak. The attacker got the signing service to sign what it wanted.

On Ethereum, the attacker sent one transaction holding 50 EIP-7702 authorisations signed by a Binance hot wallet, one for each of the next 50 nonces, so one was guaranteed to match. That turned the wallet into a sweeper the attacker controlled, and it kept sweeping new deposits for hours. Tether, Circle and others froze roughly US\$2.7 billion (about A\$3.8 billion, an estimate at about 1.42 AUD per US dollar). More than 420,000 ETH and 18,270 BTC are still out of reach.

If you run a service that signs on request, such as code signing, a token service or a payments signer, list the users and machines allowed to ask it for a signature, and check whether a burst of unusual requests would raise an alert. For Ethereum, TRM's advice is to treat a request for many authorisations across a range of nonces as a sign of compromise. Binance hasn't published its post-mortem yet, and the loss and frozen figures differ between TRM, Chainalysis, Elliptic and Binance.

## 2. Anthropic renames Max, and Ultra drops the five-hour limit

Anthropic's announcement on X, posted early Saturday Brisbane time, renames Max 5x to Max at US\$100 a month (about A\$142, an estimate) and Max 20x to Ultra at US\$200 a month (about A\$284, an estimate). Existing subscribers move over automatically. Verified Ultra accounts lose the five-hour session limit, and the weekly limit stays.

The weekly limit still bounds a long Claude Code session. If billing or runbooks still say Max 5x and Max 20x, update those names. Before you plan a session that used to stop at five hours, confirm the account is verified Ultra and read the weekly cap that still applies. The announcement doesn't describe the verification check.

## 3. Attackers hid shell commands in GitHub issue comments

The Register reports that Radware found 83 malicious issues, pull requests and comments across 61 public repositories, including Trivy, MLflow, Brave, google/langextract, dotnet/maui, Homebrew cask and github/docs. Of those, 77 were posted within 43 minutes on 1 September, from 74 accounts. The commands sat inside HTML comments, so they don't appear on the rendered page. They run when a workflow feeds that text into a shell command. Radware confirmed two cases where the payload actually ran.

Search your workflows for event text interpolated into `run` steps, including `${{ github.event.issue.body }}` and the same pattern on pull request and comment fields. Pass untrusted text through an environment variable, and keep jobs started by issues, comments or pull requests away from secrets and write tokens.

GitHub's [2 November changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/) adds brownouts on 9 and 16 November, 16:00 to 18:00 UTC, ahead of the 2 December default block on `pull_request_target` in public repositories. [W04](/blog/2026-10-29/this-week-in-developer-tech-w04) already covered that trigger.

## 4. The exploited Brotli decoder reaches .NET apps that decompress untrusted data

[Microsoft's October out-of-band .NET update](https://devblogs.microsoft.com/dotnet/dotnet-october-2026-oob-security-updates/) covers CVE-2026-111497, an out-of-bounds write in Google's Brotli decoder from versions 1.0.3 to 1.2.0. CISA added it to its exploited list on 27 October, and [Check Point's 2 November report](https://research.checkpoint.com/2026/2nd-november-threat-intelligence-report/) says automated scanning and exploitation attempts are under way. The bug was found in Node.js first. It also reaches Python's `brotli` and `brotlicffi` packages, and .NET. [RiskBits' patch rundown](https://riskbits.net/blog/monday-fix-2026-11-02/) collects the version floors.

A .NET app is exposed when it decompresses untrusted Brotli data, through ASP.NET Core request decompression, `HttpClient` automatic decompression, or `BrotliStream` and `BrotliDecoder`. Request decompression and automatic `HttpClient` decompression are off by default, so `Program.cs` and `HttpClientHandler` show whether this process accepts compressed bodies or enables automatic decompression. .NET Framework isn't affected. Microsoft rates the impact as a memory read or corruption that can lead to disclosure, crashes or privilege escalation. The HTTP2Shell nickname comes from the Node.js remote-code-execution path.

Update to .NET 8.0.33, 9.0.22 or 10.0.14, and to .NET 11 RC3 if you are on RC2. Update Node.js to 22.23.4, 24.22.1 or 26.12.1, and `brotli` and `brotlicffi` to 1.2.1. Run `dotnet --list-runtimes` on each host. Self-contained apps and container images carry their own runtime, so rebuild and republish those once the patched runtime is in the build. The same 25 October .NET release also re-ships fixes for two 13 October advisories that didn't fully land. A host that already installed those earlier packages still needs this release before those two fixes are actually present.

## 5. OpenAI's Pando backend serves concurrent monorepo pushes

[OpenAI's write-up of Pando](https://openai.com/index/scaling-git-at-openai/) explains the Git-protocol-compatible service behind its monorepo. Pando is tuned for many concurrent branch pushes and high read throughput. It keeps causal consistency per ref, stores immutable packfiles in blob storage, and reuses packs across clients with `packfile-uri`. OpenAI reports that median push latency dropped by nearly five times, and that the service moves nearly a petabyte of Git data a day. The write-up says Codex was used to build it in about 10 weeks, and that it has been live since April.

OpenAI traces how three-phase commit and write-ahead-log designs contended when unrelated branches moved, and how per-ref versions plus pack reuse avoid that contention. A reader fetching several branches can see them at different points in time. [W04](/blog/2026-10-29/this-week-in-developer-tech-w04) described a similar wait on GitHub's side, where one repository-wide lock held unrelated refs back. OpenAI is also contributing Git client changes upstream, including explicit haves and parallel pack downloads, and is exploring how to share the approach.

Pando is an internal service, and the announcement comes with no package or repository to install. On your own monorepo, time concurrent pushes to independent branches separately from pushes that update the same ref. That split shows whether a broad lock is protecting a consistency rule you still need or only making unrelated pushes wait.
