The first real report from my weekly blog scout found 57 root conversations and turned them into eight ideas. Two of them were "Automation needs memory" and "Green is not deployed".

They were not exactly wrong. They also sounded like they could have come from any developer blog, which meant the collector had worked and the scout had still missed the point.

I use Codex and Claude across enough projects that by Thursday the useful detail is spread through a week of conversations: what broke, the false lead, the command that proved it, what I changed, and whether it held up. I built a local scout to find those details across my Mac, remove the agent noise, compare them with what I have already written, and give me an HTML page to review.

Collecting the conversations worked on the first run. Teaching the scout which stories I would actually write took longer.

## The writing backlog hiding in my chat history

My conversations already work as a [rough engineering journal](/blog/2025-06-26/from-conversation-to-documentation-a-modern-dev-workflow-with-ai). If I hit an odd macOS failure, change a workflow, build a tool, or argue with an agent until the model finally matches what I meant, the path is usually captured in the thread.

I wanted the scout to do three things:

1. Find the conversations from the last successful weekly run.
2. Suggest however many posts genuinely earn a place.
3. Give me five title and structure directions for each idea so I can choose the angle before writing the draft.

The weekly run stops at the review page. It does not create posts, alter the publication queue, or publish anything. I choose the ideas first. The drafting stage can then use separate research agents to fill in the technical detail without loading every source conversation into one giant context.

## Collecting conversations across the whole Mac

Xylem hosts the routine, but the collector is not scoped to the Xylem repository.

For Codex, it inventories the locally stored active and archived sessions. For Claude Code, it starts with the local history index and joins that to the matching project transcripts.

I only want the main human conversation, so the collector removes:

- Codex subagent, execution, and automation threads.
- Claude sidechains and subagent transcripts.
- Tool payloads and non-final assistant content.

The first run looks back seven days. After that it starts at the last successful cutoff. I use a half-open time window so the same event cannot sit on both ends of consecutive runs.

There is also a 24-hour retry lookback. Every event gets a fingerprint, so a message written late into an older conversation can still be admitted without copying all of the old events into the new report.

The resulting sequence is roughly:

```text
local histories
  -> root conversations
  -> bounded conversation cards
  -> model-readable batches
  -> candidate posts
  -> validated ideas
  -> HTML review page
```

Before synthesis, the collector removes sensitive details such as project names, repository paths, email addresses, and other identifying context. It also limits message sizes. If it is uncertain about a workspace, it reduces the conversation to a broad topic summary. The model reads the prepared batches, never the raw history files.

## Making Thursday optional

My Mac is not guaranteed to be on at exactly 10:30 on Thursday morning. A weekly cron expression would be neat, but missing that one moment should not skip the whole week.

The desktop task uses a daily 10:30 Brisbane schedule. A persisted date decides whether a tick has real work to do:

```js title="The Thursday catch-up check"
return {
  due: brisbaneDate(now) >= state.nextNominalThursday,
  reason: "persisted-date",
  nextNominalThursday: state.nextNominalThursday,
};
```

Once enabled, a tick before the persisted Thursday exits successfully without doing anything. From Thursday onward, it runs until that week's scout completes. If the Mac is off on Thursday, Friday's tick still sees the overdue date and catches up.

The state also stores the last successful cutoff and any active run. If a run stops halfway through, the next tick resumes it instead of preparing a second copy. A failed or explicitly aborted run does not advance the cutoff.

That small bit of state keeps the schedule honest. The automation remembers what it finished instead of treating a timer firing as success.

The desktop scout and publisher tasks both exist, but they are paused for now because the saved scout still has the older prompt. I have run collection and synthesis manually against the real local histories. I will enable the schedule after the saved task has the revised prompt.

## Turning the week into a review page

Preparation writes bounded batches, a catalogue of the source cards, counts, and references to earlier idea reports. Synthesis processes one batch at a time and keeps only compact candidate notes between batches.

Before accepting anything, it compares the candidate with:

- Published posts.
- Tracked drafts.
- The local publication queue.
- Earlier idea reports.

Each accepted idea needs more than a title. The review page tells me:

- What actually happened.
- The reader's problem.
- The concrete product, command, failure, workflow, or result.
- What the reader gets from the post.
- Why this is something I can write from experience.
- Which proof is available for the draft.

It also adds five title directions, a short description of each angle, and an outline that follows the material.

Completion validates the result and archives the JSON for future duplicate checks. It writes a self-contained HTML file into my normal artifact folder. The page has no JavaScript or external resources, escapes every bit of generated prose, and is only readable by my user account.

The implementation has 50 focused automation tests covering the history formats, cutoff boundaries, interrupted runs, privacy checks, report validation, queue state, and publication recovery. The automation lint is clean too.

The basic commands are deliberately boring:

```bash title="Run the scout manually"
pnpm blog:state:init
pnpm blog:scout:due
pnpm blog:scout:prepare
pnpm blog:scout:complete -- --ideas /absolute/path/to/ideas.json
```

The commands are the easy part. Most of the work is deciding what the model may read and what counts as a worthwhile result.

## My first report sounded nothing like me

That first real run found 57 root conversations: 20 from Codex and 37 from Claude.

I had made the ownership classifier too conservative. Synthesis lost the specific details from every conversation and saw only broad topic counts, then returned eight ideas:

- Automation needs memory.
- Queues are real data.
- Keep the lead context clean.
- Test the interruption.
- Green is not deployed.
- Migrations need a contract.
- Measure the whole path.
- Let backlog set cadence.

It is a very tidy list of things I would never publish.

My first instinct was to improve the voice prompt. After reading a spread of older and recent posts, the problem was fairly obvious: a voice prompt can change how an idea is phrased, but it cannot turn a weak topic into one of my posts.

My posts normally start with something that happened. That might be [a misleading Azure SQL error](/blog/2025-06-18/the-mysterious-case-of-the-failing-azure-sql-deployment), [a cmux setting that changed where HTML files opened](/blog/2026-05-20/cmux-html-files-now-open-in-app), or [a knowledge cache that improved Claude's output but became annoying enough that I deleted it within a week](/blog/2026-04-07/what-i-learnt-building-a-knowledge-cache-for-claude).

The first report started with conclusions and tried to invent posts underneath them.

## Four gates made the second report mine

I added an editorial profile based on my published posts and made every idea pass four gates:

1. A first-hand seed. I encountered, built, fixed, measured, or discussed it.
2. A concrete anchor. A real product, failure, setting, command, workflow, or observable result.
3. A bounded reader payoff. One sentence saying what the reader can fix, understand, choose, or copy.
4. Available proof. A command, screenshot, reproduction, measurement, public reference, or before-and-after result.

The scout rejects generic maxims, and zero ideas is a successful weekly result.

A fresh seven-day preview found 57 root conversations and produced four concrete candidates instead of eight slogans. I chose the first three for drafting:

- Every Shunt siding starts small now.
- Why Homebrew kept making macOS think my notarized app was malware.
- This post about the scout itself.

I rejected the fourth. It was about adding line numbers and a better default to a SQL template editor. The idea was recent, concrete, and provable, so it passed the four gates. It was also basic product polish without an interesting technical problem behind it.

That exposed one more rule: publishable is not the same as interesting.

The scout now asks whether the problem has enough surprise, difficulty, consequence, or reusable learning to reward someone's time. A small feature belongs in release notes unless it uncovered a non-obvious constraint or changes how another developer would approach the work.

I made that rejection part of the [permanent editorial profile](/blog/2026-06-18/your-experience-is-a-runtime-dependency) too, so feedback on one report changes what the next report considers worth suggesting.

## What the scout does not try to do

I have kept a few deliberate limits:

- Cloud-only chats are not included because they are not available in the local histories.
- Long conversations are bounded before they enter the synthesis context.
- The Mac and desktop app still need to be running for a tick. Catch-up handles a missed date; it does not wake the computer.
- The scout suggests posts. I still decide what is worth writing.

I did not want a content machine filling a calendar. I wanted Thursday's review page to surface the stories buried in the week's conversations, with enough proof for me to decide what was worth writing.

The first report gave me eight correct-sounding slogans. The revised scout gave me three posts I might actually write. That is the result I was after.
