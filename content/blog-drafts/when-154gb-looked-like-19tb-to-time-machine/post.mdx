I was trying to work out why my 2 TB Mac kept running out of space when I definitely didn't have 2 TB of useful stuff on it. That investigation turned into a second problem: after clearing the backup destination and starting Time Machine again from scratch, the fresh 4 TB share filled up too.

The source Data volume contained about 1.78 TB. The new backup image reached roughly 3.7 TB, then Time Machine stopped because the destination had fallen below its required 100 GB reserve.

```text title="Time Machine log"
Insufficient free space after thinning all available backups
free space: 98.76 GB, minimum free space: 100 GB
BACKUP_FAILED_TARGETVOL_DISK_FULL (56)
```

Those numbers didn't make sense until I stopped asking which folders were large and started asking a slightly different question: how large did each file *appear* to be?

## Allocated size and apparent size are different

I use [Shunt](/projects/shunt) to run parallel development environments as isolated Apple container guests. The guests are intentionally cheap to create and throw away, but the Apple Container runtime needs somewhere to store their filesystems.

On my Mac, that runtime state lives here:

```text title="Apple Container runtime path"
~/Library/Application Support/com.apple.container
```

A normal `du` check showed a large but believable folder:

```bash title="Measure allocated disk usage"
du -x -sh "$HOME/Library/Application Support/com.apple.container"
```

```text title="Allocated size"
154G    /Users/.../Library/Application Support/com.apple.container
```

Then I asked `du` for the apparent size instead:

```bash title="Measure apparent size"
du -x -A -sh "$HOME/Library/Application Support/com.apple.container"
```

```text title="Apparent size"
19T     /Users/.../Library/Application Support/com.apple.container
```

That was the missing detail: sparse files.

A sparse file can claim a huge logical size without allocating blocks for all the empty space. One of my `rootfs.ext4` files was 513 GiB logically but used about 18 GiB of blocks. Others were 512 GiB logically while using less than 1 GiB locally.

Apple's containerization code creates a per-container `rootfs.ext4` and unpacks the image into it. You can see that shape in the [Apple containerization source](https://github.com/apple/containerization/blob/main/Sources/cctl/RunCommand.swift#L2120-L2156). There is also an [issue in Apple's container repository describing the same Time Machine over SMB behaviour](https://github.com/apple/container/issues/612): generous sparse ext4 images become much larger when the backup path does not preserve their holes as expected.

APFS was doing its job on my Mac. The problem appeared when those sparse files crossed into the network Time Machine backup. The backup consumed far more destination space than the files consumed locally.

## Shunt has two kinds of data worth separating

This matters for Shunt because there are two storage layers with different trade-offs.

The Apple Container runtime has guest root filesystems, snapshots, image blobs and BuildKit state. I can recreate those. They do not need to be in Time Machine.

Shunt also has host-side siding data under paths shaped like this:

```text title="Shunt siding data layout"
~/Developer/github/<org>/.shunt-dev/<project>/<siding>/vol
```

Those `vol` folders can contain cloned local databases or other environment data. Mine are reproducible, so I exclude them too. That is a choice, though. If your local database contains test state you cannot recreate, back it up deliberately before excluding it.

I do not blanket-exclude every `.shunt-dev` directory. A siding source worktree may contain uncommitted work, so source and runtime data should not be treated as the same thing.

APFS clones add another wrinkle. Several siding trees may report a large logical total while sharing blocks locally. A backup destination that does not preserve that clone relationship can store those trees as independent copies. Shared locally does not automatically mean shared after a backup crosses filesystems or formats.

## Excluding the runtime takes one command

You can manage exclusions through **System Settings > General > Time Machine > Options**. Apple documents that flow in [Exclude files from a Time Machine backup on Mac](https://support.apple.com/guide/mac-help/exclude-files-from-a-time-machine-backup-mh15622/mac).

For repeatable developer-machine setup, `tmutil` is easier:

```bash title="Exclude Apple Container runtime state"
runtime="$HOME/Library/Application Support/com.apple.container"

tmutil addexclusion "$runtime"
tmutil isexcluded "$runtime"
```

The check should return:

```text title="Expected exclusion state"
[Excluded]  /Users/.../Library/Application Support/com.apple.container
```

The plain `addexclusion` form creates a sticky exclusion that follows the directory if it moves. I deliberately do not use `-p`, because fixed-path exclusions need elevated privileges and are unnecessary here.

One detail caught me while testing this: excluded items still appear in local Time Machine snapshots. Apple calls that out in its documentation. If you delete a large excluded folder and Finder still shows the old free-space number, an existing local snapshot may be retaining those blocks until Time Machine finishes or macOS purges the snapshot.

## Keeping build output out as projects change

The single runtime exclusion fixes the spectacular failure, but developer machines grow new disposable folders constantly: `.NET` creates `bin` and `obj`, Rust creates `target`, JavaScript projects create `node_modules`, SwiftPM creates `.build`, and Xcode has Derived Data and Simulator state.

Time Machine does not support an exclusion glob, so I keep a small config-driven script that scans my development roots and marks the real directories. The core operation can be as small as this:

```bash title="Exclude common generated folders"
find "$HOME/Developer" \
  -type d \( \
    -name bin -o \
    -name obj -o \
    -name target -o \
    -name node_modules -o \
    -name .build \
  \) -prune -print0 \
  | xargs -0 -n 100 tmutil addexclusion
```

My version first checks the exclusion xattr and sends only new paths to `tmutil`. That matters on a large development tree because reapplying thousands of unchanged exclusions makes Spotlight acknowledge a lot of pointless metadata work.

I also run it daily and clean exact `src-tauri/target` directories through Cargo:

```bash title="Clean one Tauri build directory"
cargo clean \
  --manifest-path /path/to/src-tauri/Cargo.toml \
  --target-dir /path/to/src-tauri/target
```

After cleaning, the script recreates the empty target directory and reapplies its Time Machine exclusion. Otherwise `cargo clean` can remove the directory along with the sticky xattr, and the next build becomes eligible for backup again.

## What this means for other backup tools

I reproduced the failure with Time Machine over SMB, so that is the claim I can make confidently. Other backup tools and destinations handle sparse files differently.

The risk itself is general. A backup or copy tool needs to preserve sparse extents, and the destination filesystem needs to support them. Rsync, for example, has an explicit [`--sparse` option](https://download.samba.org/pub/rsync/rsync.1#opt--sparse) and warns that the result depends on destination filesystem and kernel support.

So before pointing any backup product at VM disks, container filesystems or database images, compare allocated and apparent size. Then check whether that exact source-to-destination path preserves sparse files and clone semantics. The fact that a folder uses 154 GB on APFS does not guarantee it will use 154 GB in the backup.

## The second first backup

After excluding Apple Container and the reproducible Shunt data stores, I cleared the failed destination and started again. At about 26% through, the replacement backup had used 630 GiB and still had roughly 3 TiB free. Time Machine estimated about 1.55 TB of eligible source data instead of the earlier 1.78 TB.

That run was still in progress when I captured the numbers, so it was not a completed-backup result yet. The early shape was materially different from the failed attempt: 630 GiB used with 3 TiB free, rather than 3.7 TB used with less than 100 GB free.

The check I am keeping is simple: measure both allocated and apparent size before backing up disposable runtime state. Source code belongs in version control, important data needs a deliberate backup, and a 512 GiB sparse container disk that I can recreate does not need to follow me into Time Machine.
