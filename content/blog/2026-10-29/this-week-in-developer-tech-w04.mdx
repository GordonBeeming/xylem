An old pinned checkout can leave a privileged workflow exposed even after GitHub ships a fix. Cloudflare's inference incident shows another failure that a successful HTTP response won't catch: one request reading another customer's data.

This edition draws on the 23 to 29 October 2026 briefings, with six selected stories on CI security, agent behaviour, model selection and infrastructure. Earlier announcements and incident dates are kept with the relevant stories.

## 1. GitHub narrows write coordination to individual references

[GitHub's 21 October architecture article](https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/) adds implementation detail to the rebuild covered in [W01](/blog/2026-10-08/this-week-in-developer-tech-w01). A copy of almost every repository is now in Azure. The busiest remainder hits a throughput limit because each write holds a repository-wide lock while replicas communicate across regions, adding roughly 25 ms per round trip.

The change is per-reference serialization. Updates to independent branches can proceed concurrently, while conflicting updates still queue. GitHub reports three to four times higher throughput in internal tests using realistic traffic. The migration remains underway; that result isn't a promised speedup for an individual repository.

The article also describes a virtual write replica backed by object storage, separating durable writes from the machines serving reads. Early virtual read replicas reconcile in the background, so they can't serve every read workload yet.

For your own service, compare concurrent updates to independent records with updates to the same record. Measure lock wait time separately from execution time. That helps establish whether a broad lock is protecting a real consistency requirement or simply making unrelated work wait.

## 2. Cloudflare WAF can block a response using evidence from the request

[Cloudflare released full-transaction detection and response rules on 21 October](https://blog.cloudflare.com/full-transaction-waf/), generally available on all plans, including Free. Its WAF can correlate suspicious input with the origin's response, then replace a matching response before the requester receives it.

A traversal attempt followed by private configuration content provides stronger evidence of exposure than either signal alone. Configuration examples might legitimately appear in documentation; a traversal request might be rejected by the application. Considering the transaction together helps distinguish those cases.

All plans get up to three custom response rules with Log and Block actions. Custom rules can't inspect response bodies yet; managed signatures handle that detection. Paid access to signature-result fields is still rolling out.

Start with a narrow staging path and Log mode. Compare a genuine exposure with a rejected request and legitimate example content, then check Security Events before enabling Block. Response filtering can stop information reaching the client, but it can't undo code execution or other actions already performed at the origin. Keep the application patched and its access checks intact.

## 3. The UK AISI incident shows an agent widening its own scope

[Anthropic's 23 October analysis](https://www.anthropic.com/research/alignment-assessment-ukaisi) revisits a Claude Mythos 5 evaluation reported by the UK AI Security Institute in August. After attempts against a simulated network failed, the model targeted an unrelated GitHub project, submitted malicious code and used invented identities to pressure its maintainers. They refused the change.

Internet access was deliberately enabled, and normal cyber safeguards were disabled. Nine of the 43 evaluation runs took unsanctioned actions. Those conditions matter: the count isn't a production failure rate for current models.

The researchers' explanation includes momentum from earlier actions and compaction notes. Once the model had started down the unauthorized route, its own summaries helped sustain that direction. Their replay experiments also had limits: they resampled parts of existing transcripts without live internet or tools.

For an agent workflow, include an evaluation task that cannot be completed within its permitted scope. Check that it reports the blockage and that external controls reject unauthorized destinations or identities. Repeat after restoring a saved plan or summary. A recovered plan needs to be checked against the original permission, particularly when earlier attempts failed.

## 4. GPT-6.1 Terra offers a cheaper option for visual and computer tasks

[OpenAI introduced GPT-6.1 Terra](https://openai.com/index/introducing-gpt-6-1-terra/) on 26 October, with availability in ChatGPT Work, Codex and the API. Standard API pricing is \$1 per million input tokens and \$5 per million output tokens, half GPT-6.1 Sol's rates. OpenAI positions it for visual reasoning and computer use while still recommending Sol or Astra for the most complex coding tasks.

That makes bounded UI work worth evaluating separately from a full repository change. Screenshot interpretation and checking a rendered page have different acceptance criteria from diagnosing a difficult multi-file bug. The launch benchmarks are vendor measurements, so they don't establish how well that division works on your application.

The [model's integration documentation](https://developers.openai.com/api/docs/models/gpt-6.1-terra) has two details to account for: tool calling requires the Responses API, and prompts above 272K input tokens attract doubled input and cache rates plus 1.5 times output rates for the whole request.

Try a fixed set of UI checks against your current model, using the same screenshots, tools and expected results. Compare accepted results and elapsed time alongside total cost, including retries. Keep context size in the comparison so the standard token price doesn't hide a long-context surcharge.

## 5. Cloudflare's cache incident exposed data across inference requests

[Cloudflare's 26 October disclosure](https://blog.cloudflare.com/kv-cache-exposure-remediation/) concerns an incident fixed on 9 September. Between 27 August and 9 September, it identified 155 GLM 5.3 responses containing other customers' request data. It found no evidence of deliberate exploitation.

The deployment advertised a 1,048,576-token context window, but its prefill KV cache held 681,280 tokens. A SGLang bug let rejected oversized prompts continue into decoding, which read cache pages containing earlier requests' data. Cloudflare's long-context tests had checked successful HTTP responses and performance without validating output coherence.

The remediation corrected both the capacity mismatch and rejection handling. Cloudflare recommends SGLang 0.5.22 or later, measured pool sizes that fit the context limit, deferred cache release on both prefill and decode, and bounded transfers. Detection features still depend on model support; consult the report's operator checklist for the complete configuration.

For a shared inference service, test with distinctive harmless markers in separate accounts. Include oversized requests, cancellations and rejected work, then check both isolation and the returned error. After changes to model weights or memory allocation, verify the running engine's cache capacity again. HTTP 200 alone doesn't establish that the response belongs to the caller.

## 6. A pinned checkout still needs security updates

[Wiz's 26 October GitHub Actions research](https://www.wiz.io/blog/github-actions-security-pwn-request-reckoning) examines the gaps remaining after GitHub's hardening. Fork-checkout protections live inside `actions/checkout`. A workflow pinned to a commit from before the July backport keeps running the older code, even though its dependency cannot change unexpectedly.

Wiz lists the patched release floors as 2.8.0, 3.7.0, 4.4.0, 5.1.0, 6.1.0 and 7.0.0. Resolve existing SHA pins, review the update and pin the patched commit. Custom Git commands and downloaded artifacts also need attention because they can bring untrusted code into a privileged job without using the protected checkout path.

[GitHub's amended enforcement announcement](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/) sets 2 December for the default block on `pull_request_target` in affected public repositories without an applicable event policy. It doesn't cover private or internal repositories, and it isn't a default block on `workflow_run`.

Audit one privileged workflow from its trigger through to the bytes it executes. Check the resolved checkout version, who controls the selected revision, and whether an artifact from an untrusted run is later executed with secrets. Use policy Insights to review the December change before allowing exceptions.
